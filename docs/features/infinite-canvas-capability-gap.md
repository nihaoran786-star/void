## 1. 一页结论

**今天在 Void 的无限画布上，你能做这些事：**

1. 打开任意本地工作区的画布，拖出一块无限大的白板；上面可以放文字卡、
   图片卡、视频卡，卡与卡之间可以拉线，能平移、能缩放、能删，关掉页签
   再打开状态还在（每个工作区一份画布文档，自动存盘）。
2. 新建一张空白生成卡，在卡上写一段提示词，从 **317 套风格**里挑一套，
   点"生成"——图直接落进这张卡。这一步不经过左边的主 AI，点一下就直接
   走出图管线，不烧模型上下文。
3. 把几张图片卡用线连到一张卡上，它们就成了这张卡的"垫图参考"，卡上按
   连线顺序标出"图一 / 图二"，提示词里可以直接 @图一、@图二。
4. 已经有图的卡上，有五个按钮：放大、扩图、局部重绘、擦除、抠图。点任一
   个都会弹出一个补全指令的小窗，确认后**在旁边长出一张新卡并连回原卡**
   ——原图永远不会被覆盖，等于自带版本树。
5. 视频卡：可以从文字直接出视频，也可以从一张图片卡派生出视频卡。
6. 在会话里可以直接让主 AI 指挥画布："帮我把这些卡排成三行""给这张图再
   生成一版"——AI 有一套读画布 / 改画布的工具，改动会记进待办日志，画布
   下次打开会自动补做。
7. 出图过程中把画布关掉也不会丢：重开时系统会自己对账，把完成的落卡、
   把不确定的标成可重试的失败。

**还差什么（一句话）：** 画布现在是一条**能用的单件出图流水线**，但还不是
一块**顺手的创作台**——看图看不大、参数调不了、一次只能出一张、手滑了不
能撤销、精修全靠打字描述而不能圈选，后期（剪辑、配音、3D 预演）整块为零。

一个更直白的对比：kunpeng 的画布已经是"白板 + 生产队列 + 精修室 + 剪辑室
+ 项目管理"的合集；Void 的画布目前是其中**白板 + 出图**这一段，做得扎实
（持久化、幂等、失败可解释、AI 可指挥都在），但边上的四间房还没盖。

## 2. 已具备清单（逐项对照 kunpeng）

✅ = 我们有；⚠️ = 有但实现方式不同或能力更弱。

| 能力 | Void 现状 | 与 kunpeng 的差异 |
|---|---|---|
| 无限白板（平移 / 缩放 / 拖动节点 / 连线 / 删除） | ✅ | 同为 React Flow；我们没开小地图、没配吸附 |
| 视口记忆、关闭再打开状态不丢 | ✅ | 我们把视口写进文档；kunpeng 存本地缓存 |
| 文字卡 / 图片卡 / 视频卡 | ✅ | kunpeng 另有音频卡、全景卡、分组卡 |
| 多选与框选 | ⚠️ | 只是 React Flow 的默认行为，我们没有配置、没有测试、没有多选工具条 |
| 文生图（空卡出图） | ✅ | 同 |
| 垫图参考（连线即参考，带顺序角标） | ✅ | 我们最多 图一…图十；kunpeng 还支持分组卡整组当参考 |
| 风格库 | ✅ 317 套（电影感 67 / 二维动画 94 / MJ 84 / 动态图形 72） | 数据同源；我们**没有缩略图**，只能看名字选 |
| 五件套（放大 / 扩图 / 局部重绘 / 擦除 / 抠图） | ⚠️ | **我们是"指令驱动"**：把操作写成一段提示词交给通用出图模型；kunpeng 每项走专用通道（放大走 **Topaz**，重绘走 gpt-image-2 + 红色蒙版）。效果上限因此由当前 APIMart 模型决定——这是复用管线的既定取舍 |
| 派生而非覆盖（版本树） | ✅ | 我们把"有图的卡一律派生"写成了测试断言的不变量，比 kunpeng 更严格 |
| 失败可解释、可重试、不永远转圈 | ✅ | 七类错误码 + 卡上失败块；kunpeng 靠队列面板重试 |
| 关画布期间完成的任务能补回来 | ✅ 落盘批次对账 | kunpeng 无同等机制（靠队列常驻） |
| AI 指挥画布（增删改排布、代发生成） | ✅ `CanvasRead` / `CanvasOp` + 待办日志 + 水位对账 | kunpeng 工具更多（自动布局、批量建卡、截图节点）；我们更保守：AI 不能删带媒体的卡、不能改 mediaRef、不能建分组卡 |
| 图生视频 / 文生视频 | ✅ | kunpeng 视频引擎选择面更宽（Seedance / 海螺 / 首尾帧等） |
| 出图不经主 AI（直连管线） | ✅ `submit_infinite_canvas_media_job` | kunpeng 同样是前端直连；这条我们已对齐 |
| 权限与边界（远程工作区拒收、跨工作区拒收、路径越界拒收） | ✅ 比 kunpeng 严 | kunpeng 是单机单用户，没有这层 |

**变体派生**：kunpeng 有一个"生成变体"按钮；我们的"再生成"在语义上等价
（沿用提示词 + 原图当参考、派生新卡），差别只在按钮命名与是否自动带图，
故不单列为差距。

## 3. 差距清单（按"对用户价值 × 实现成本"排档）

工作量档位口径：**小** ≈ 一两天一个人；**中** ≈ 一周内一个切片；
**大** ≈ 需要单独立项、跨前后端或引入新依赖。

### P1 — 建议立刻补（用户天天撞到，成本可控，无新模型/新渠道）

| # | 用户视角一句话 | 我们缺什么 | 工作量 | 依赖 |
|---|---|---|---|---|
| P1-1 | "图出来了但我看不清，也存不下来。" | 节点全屏查看器（点图放大、可缩放拖动、另存到本地）。今天卡片里只有一张小缩略图，没有任何放大或下载入口 | 小 | 无 |
| P1-2 | "我想换个模型 / 改比例 / 改尺寸，界面上根本没有地方点。" | 生成参数弹层（模型、尺寸/比例，视频再加时长）。后端 `GenerateImage` 已支持这些字段，前端一个都没暴露，全走默认值 | 中 | 无（后端已就绪） |
| P1-3 | "一次只出一张，挑不出满意的。" | 批量出图 n>1 并落成多张卡。直连网关目前把 `n` 写死为 1；后端 schema 允许 1–4，但默认模型 `gpt-image-2` 只支持 1，所以必须与 P1-2 的模型选择同期做才有意义 | 中 | 无新渠道，但**必须与 P1-2 捆绑** |
| P1-4 | "手滑删错了、拖乱了，救不回来。" | 撤销 / 重做。画布文档有版本号和 CAS，但没有任何历史栈 | 中 | 无 |
| P1-5 | "复制一张卡、右键做点什么——都没有。" | 复制/剪切/粘贴/再制、右键菜单（节点菜单 / 空白处菜单 / 多选菜单）、多选浮动工具条 | 中 | 无 |
| P1-6 | "十几张图在跑，我不知道跑到哪了。" | 任务队列面板（进行中 / 排队 / 已完成，可重试、可取消）。今天只有每张卡各自转圈，没有全局视图，也无法取消 | 中 | 无（取消需后端加一个中止入口，小改） |

P1 六项合起来的性质：**全部是"画布作为工作台"的基本功**，没有一项需要新
模型、新渠道、新密钥或新依赖库，绝大部分只动前端面板与直连网关。

### P2 — 值得做（价值高但更重，或需要一点新工程）

| # | 用户视角一句话 | 我们缺什么 | 工作量 | 依赖 |
|---|---|---|---|---|
| P2-1 | "我想圈出这块重画/擦掉，而不是用文字描述位置。" | 蒙版画笔。kunpeng 的做法不需要新模型：在原图上画红色标记，把"原图+红标"合成一张参考图，提示词里指"红色标记区域"——通用图像模型就能定位。这能把我们最弱的"局部重绘/擦除"从玄学变成可控 | 中 | 无新模型；需前端画布绘图（canvas 合成） |
| P2-2 | "拖动的时候没有参考线，排不齐。" | 对齐辅助线 + 吸附网格 | 小 | 无 |
| P2-3 | "我只想要图里的一部分。" | 裁剪（框选区域 → 裁出一张连线的新卡，不动原图） | 小 | 无（浏览器端裁剪） |
| P2-4 | "给我一张九宫格分镜，然后拆成九张卡。" | 分镜拆分器：把网格图按 2×2 / 3×3 / 5×5 切成独立卡片；再往上是"剧情推演四宫格""多机位九宫格"这类成套派生指令 | 中 | 无（切图在前端） |
| P2-5 | "这张图是怎么画出来的？帮我倒推提示词。" | 图生提示词。需要一条"图 → 文字"的视觉分析调用 | 中 | 需要一个能读图的模型入口（现有渠道可能已能覆盖，需先确认） |
| P2-6 | "机位、镜头语言我说不清楚。" | 机位/镜头预设库（纯提示词片段，多选累加进提示词），与风格库同一形态 | 小 | 无（数据即可） |
| P2-7 | "风格只有名字，我不知道长什么样。" | 风格缩略图。第一期明确"不出缩略图"，选风格全靠猜 | 中 | 需要一批示例图资产（体积与许可要单独确认） |
| P2-8 | "画布上的角色图，AI 短剧中心里能直接用吗？" | 画布 ↔ **现有 AI 短剧中心**（Short Drama center）双向同步（即计划里的 K3、`domainRef` 赋值）。对标产品所说的"流水线工坊"在 Void 里对应的就是已经存在的 AI 短剧页面，复用现有 short-drama 领域模块与 `ShortDramaCenterPanel`，**不新建工坊**。契约字段已预留，无任何实现 | 大 | 无新依赖，但跨两个受保护域，需单独立项与回归护栏 |
| P2-9 | "常用的角色/场景/音色，每次都要重新找。" | 资产库面板（可复用的角色 / 商品 / 场景 / 音色，选中即注入参考） | 大 | 与 P2-8 天然同期 |
| P2-10 | "把线拖到空白处，让它直接给我建一张卡。" | 悬空连线 → 浮动菜单建新卡；节点缩放手柄 | 小 | 无 |

### P3 — 可选（价值真实但不紧迫，或成本明显偏高）

| # | 用户视角一句话 | 我们缺什么 | 工作量 | 依赖 |
|---|---|---|---|---|
| P3-1 | "把这一组卡框起来当一个场景。" | 分组卡渲染（嵌套拖拽、父子坐标、折叠）。持久化契约里已有 `group`，但没有 UI，且 AI 被明确禁止创建 | 中 | 无 |
| P3-2 | "我想同时开好几个画布项目。" | 多文档 / 项目切换（今天是每个工作区一份画布） | 中 | 无 |
| P3-3 | "把这个项目打包发给别人。" | 项目导出/导入（打包画布 + 资产 + 路径重写） | 中 | 无 |
| P3-4 | "给这段视频配个旁白。" | 配音卡 / 音频卡。后端其实已经有 `GenerateSpeech` 与 `TranscribeAudio` 工具，画布上没有音频节点类型 | 中 | 无新渠道（工具已在） |
| P3-5 | "选中两三张图，各圈一块拼成一张。" | 多图标注融合 | 中 | 无新模型（同 P2-1 的红标思路） |
| P3-6 | "真正的无损放大。" | 专用放大通道（kunpeng 用 Topaz）。我们的"放大"目前是指令化提示词，效果上限受限 | 中 | **需要新渠道/新密钥** —— 与"不引入新 Provider"的既定前提冲突，须业主先松口 |
| P3-7 | "先用白模摆好机位再出图。" | 导演台 3D 预演（三维人偶、机位关键帧、白模转成片） | 大 | 需引入 three.js 及一整套编辑器；单独产品级立项 |
| P3-8 | "视频里这句说错了，帮我剪掉。" | 时间线 / 转写剪辑 / 字幕导出 | 大 | 需 ffmpeg 管线（见 §4） |

### 不做（见 §4 理由）

AI 剪辑代理、完整 NLE 剪辑引擎、花字/动态图形模板库、剪映工程导出、
实时多人协作、Web 分享链接。

## 4. 明确不做及理由

1. **AI 剪辑代理与完整非线性剪辑引擎（NLE）** —— 此前评估结论为不建议
   移植，本次读码后维持该结论。它在对标产品里是一整套自成体系的工程
   （多后端渲染图、ffmpeg 多趟导出、独立撤销栈、词级转写与静音检测），
   与 Void"对话为中心 + Canvas 只做呈现"的架构没有耦合点，移植等于在
   Void 里再养一个剪辑软件。若业主真的需要剪辑，正确形态是**导出到成熟
   剪辑软件**，而不是内置。
2. **花字 / 动态图形模板库（250+ 页面模板）** —— 依附于上面的剪辑引擎，
   单独搬进来无处落地。
3. **剪映工程导出** —— 依赖上面的时间线数据结构，前置不成立。
4. **实时多人协作** —— 对标产品其实也没有（它的"协作"是单机内画布↔流水线工坊
   ↔Agent 的同步；在 Void 里对应画布↔现有 AI 短剧中心↔Agent）。Void 的画布文档是单写者 + CAS 模型，改成多人实时需要
   换一整套冲突解决方案，与当前产品阶段不匹配。
5. **Web 分享链接** —— 桌面端本地工作区模型下没有可分享的服务端载体；
   要做也只能做成 P3-3 的打包导出。
6. **远程工作区上的画布** —— 维持现状 fail-closed。与 Workspace Media
   的既定边界一致，解锁前提是 `remoteConnectionId` 贯通文件 IO。
7. **新 Provider / 渠道 / 密钥（含 Topaz 放大）** —— 除非业主明确松口。
   这是 K2 立项时的核心前提，本文档不擅自推翻，仅在 P3-6 记下代价。

## 5. 建议的第四期（K4）范围

**一句话：** 第四期不加新的生成能力，只把画布从"能出图"做成"顺手"——
**看得清、调得动、错得起、跑得明白**。

**建议切片组合（全部来自 P1）：**

| 切片 | 内容 | 规模 |
|---|---|---|
| W1 | 节点全屏查看器 + 另存本地（P1-1） | 小 |
| W2 | 生成参数弹层：模型 / 尺寸 / 比例（视频加时长）（P1-2） | 中 |
| W3 | 批量出图 n>1，多结果落成多张派生卡（P1-3，依赖 W2） | 中 |
| W4 | 撤销 / 重做（P1-4） | 中 |
| W5 | 复制粘贴 / 再制 / 右键菜单 / 多选工具条（P1-5） | 中 |
| W6 | 任务队列面板：进行中·排队·完成，可重试可取消（P1-6） | 中 |
| W7 | 顺带补齐：对齐辅助线与吸附（P2-2）、悬空连线建卡与节点缩放（P2-10） | 小 |

**为什么是这一组（自洽性）：**

- **同一个用户痛点链条**：出图 → 看结果 → 不满意就换参数再出 → 出多张挑
  一张 → 挑的过程中会拖会删会撤销 → 想知道一堆任务跑到哪了。这七片正好
  首尾相接，缺任何一片体验都断。
- **零新渠道、零新密钥、零新模型**，与 K2/P3 的既定前提完全一致。
- **几乎不动后端**：W2/W3 是把后端已有的字段接到前端；W6 的"取消"是唯一
  一处小的后端新增；其余全在画布面板内。
- **风险面小**：不碰短剧运行时、不碰 `attach_short_drama_media_result`、
  不改画布文档的 schema（撤销栈可以只活在内存里，不进磁盘契约）。
- **粗略规模**：约 1 个中等切片周期，7 片里 2 小 5 中，与 K2、P3 单期体量
  相当。

**建议放到第五期（K5）而不是塞进第四期的**：蒙版画笔（P2-1）与分镜拆分器
（P2-4）——两者价值都高，但都需要在画布里引入一块新的图像编辑子界面，
和第四期"只做工作台基本功"的主题不同源，混在一起会让验收面失焦。

## 6. 已知取舍备忘（容易重犯的坑）

1. **预览一律走 data URL，不能用资产协议。** 桌面端没有开启 Tauri 的
   `assetProtocol`（`tauri.conf.json` 里根本没有这一节），`convertFileSrc`
   生成的流式 URL 会被 webview 直接拒绝。所以画布卡片的图片/视频预览
   必须带 `forceDataUrl: true` 走 `resolveWorkspaceMediaPreviewUrl`
   （图片进有界缩略图缓存），与 Workspace Media 图库同款。**任何"顺手
   优化成流式 URL"的改动都会让画布整片白图。** 代价是大视频文件的预览
   偏重——这是明知的取舍，不是缺陷。
2. **画布按钮不经主 AI。** 生成 / 再生成 / 五件套走
   `submit_infinite_canvas_media_job` 直连管线；会话路径只保留给"用户在
   会话里让主 AI 出图"。`SessionImageGenerationGateway` 与
   `ImageToolPlaceholderGateway` 仍在仓库里但面板已不使用，改动时不要
   误以为它们是活路径。
3. **折叠工具经 `CallDeferredTool` 网关调用**，前端任何按原始 `toolName`
   过滤事件的写法都会漏掉它们——要按回执形状匹配。这条已经踩中两次。
4. **有图的卡的 `mediaRef` 在任何路径下都不可变更**，这是测试断言的不变量；
   新增能力时不要为了"省一张卡"去覆盖原图。
