# AI 客服（微信自动回复 + 工作区知识库 + 双层监督）设计

日期：2026-07-22（同日修订：补充策略引擎与身份-上下文模型；2026-07-23 补充决策记录与 POC；2026-07-23 定稿呈现模型与 cowork 门控）

## 决策记录（2026-07-23）

- 产品核心一句话：**AI 接管号主微信，自动回复好友**。不以前置的观察模式/建议模式作为必经阶段；白名单、黑名单、群聊开关、静默时段、熔断、限速全部保留为配置项，默认配置即"全部好友自动回复 + 群聊关闭 + 夜间静默"。
- 评审采纳项保留在工程层而不改变产品姿态：发送意图先持久化、无法确认发送结果时不自动重试、身份无法确认时不回复、配置单写者（守护进程）+ revision、巡检只产建议补丁、合规检查作为正式发布 Gate。
- POC 已落地：`prototypes/ai-customer-service/`（独立 Python 守护进程，契约与本文件 config/status/contexts/knowledge 完全一致，验证后按呈现层方案收编进 core）。
- 呈现定稿（多轮交互样机评审确认）：三主态信号 `signal: on | off | attention` + 大白话 `reason`，由守护进程/看门狗显式写入，UI 不推断；健康信息全隐身（窗口/巡检/计数平时不显示，异常才出现并写明原因与主操作）；身份待确认降级为不打断主信号的琥珀 micro pill。
- 回复范围两级模型：`全部回复`（默认）/ `指定回复`；白名单与黑名单为两个独立名单页，逗号分隔批量输入即时计数；白名单为空 → `signal: attention`；切回全部回复名单保留并提示。
- 面板**无会话区**：逐会话上下文、指纹去重、接管检测归守护进程；号主在微信中亲自回复时守护进程自动检测并对该会话静默。
- 视觉定稿：HERO 大环 + 今日节奏流线 + 三行配置的极简结构；随软件 void-light 主题，样式全走语义 token，不硬编码色值。
- **cowork 门控**：AI 客服为 cowork 会话模式专属能力，仅 `session.mode === 'cowork'` 的会话出现面板入口与守护启用入口；门控判定在服务模块，UI 只接线。

## 目标

在 cowork 体系上新增一个**外部挂载的持久化 AI 客服能力**：AI 操作本机 Windows 微信客户端，**接管整个微信号**——默认凡来信必回，回复范围由策略引擎（黑名单/白名单/群聊开关）决定；客服知识以工作区内 markdown 知识库形式挂载；每个客户的上下文按内部 customer_id 物理隔离；工作区主会话作为巡检总管，每 30 分钟审查一次，出现故障时按阶梯纠正或重启，修不好则升级人工。AI 客服为 cowork 会话模式专属能力，仅 cowork 会话可开启。

## 非目标

- 不做微信协议逆向、进程注入、hook；只走 UI 自动化（UIA/MSAA → OCR → 视觉降级）。
- 不做企业级多渠道客服中台（工单、SLA、多坐席）；本期只覆盖个人微信单账号、低频客服场景。
- 不新建向量/embedding 检索基建；知识库 v1 使用 markdown + 现有字面搜索。
- 不复用 `remote_connect/bot` 网关——该网关方向是"IM 遥控本软件"，与本设计"本软件操作微信客户端"方向相反。

## 背景与现有底座

- `src/apps/desktop/src/computer_use/`：生产级 Computer Use，Windows 一等公民。`windows_ax_ui.rs` / `windows_msaa.rs`（UIA/MSAA 定位）、`windows_bg_input.rs`（后台输入，含逐字符 `WM_CHAR` 投递与 SendInput 降级）、`windows_wgc_capture.rs` + `screen_ocr.rs` + `som_overlay.rs`（视觉兜底）。
- `src/crates/core/src/agentic/tools/implementations/computer_use_*.rs`：对 agent 暴露 `click_target`（AX → OCR → 坐标一次解析自动降级）、`app_type_text`、`key_chord`、`list_apps`、`get_app_state` 等高层动作，cowork 模式可直接调用。
- `src/crates/core/src/service/cron/`：CronService + `jobs.json` 持久化 + DialogScheduler，可把定时 agent 回合投递进绑定会话；`docs/features/automation-phase-a-behavior.md` 明确支持 cowork 会话作为执行模式。30 分钟巡检直接复用，不新建调度器。
- 工作区隔离底座：`~/.void/projects/<slug>/` 下已有 `sessions/`、`memory/`、`plans/` 等，新增 `knowledge/` 与客服状态文件遵循同一模式。
- `src/crates/core/src/agentic/tools/implementations/skills/`：`SkillModeId::Cowork` 策略钩子，用于挂载客服人设与"先查知识库再作答"纪律。

## 总体架构

```text
客服守护进程（新组件，core 常驻服务）
  轮询微信窗口 -> 增量解析新消息 -> 策略判定（回复范围）
  -> 身份解析（customer_id）-> 检索 knowledge/ + 该客户上下文
  -> LLM 生成 -> 拟人输入发送
  每个周期写 status.json 心跳

第一层 看门狗（确定性代码，core 内，百行级）
  进程存活 / 心跳时效 / 微信窗口存在性 -> 修复阶梯 -> 熔断 -> 报警

第二层 LLM 巡检（现有 Cron，每 30 分钟唤起主会话/cowork 会话）
  读 status.json + 近期会话记录 -> 语义审查（质量/幻觉/知识缺口/异常模式）
  -> 调提示词 / 补知识库 / 改配置 / 触发重启 / 通知人工
```

依赖方向保持 `UI / route -> Module Interface -> Adapter / service -> 外部系统`：客服守护进程是 service 层组件，UI 只消费其显式状态（status.json 映射的视图模型），UI 不得从空数组或原始字符串推断运行状态。

## 客服守护进程

### 监听循环

- 按 UIA 类名 `WeChatMainWndForPC` 定位主窗口；轮询间隔默认 3 秒（可配 2~10 秒）。
- 监听面是整个账号的会话列表，不是预先登记的特定联系人；任何来信都进入策略判定。
- 增量跟踪：记录每个会话的已读位置（消息指纹哈希 + 持久化游标），只处理增量，重启后从游标恢复，不重复回复。
- 消息类型：v1 只自动回复文本；图片/语音/文件/转账/系统消息记录并跳过，必要时提示人工。

### 应答管线

0. **策略判定**（见下节）：不在回复范围内 → 记录并跳过，不入队。
1. **身份解析**：消息来源映射到内部 `customer_id`（见身份绑定节）。
2. 新消息入队（每客户串行，跨客户并发受限）。
3. 检索 `knowledge/` + 加载该客户上下文：先 FAQ 关键词命中（话术零偏差优先），未命中再由 LLM 基于检索片段与该客户历史生成，禁止脱离知识库自由发挥敏感事实（价格、承诺、政策）。
4. 拟人发送（见下节）。
5. 全部收发写入客服日志与该客户上下文（供巡检审查与审计）。

### 拟人发送

- **阅读延迟**：收到后等待 `len(消息) × 50~100ms` 再开始回复。
- **混合输入**：短回复（≤80 字）走逐字 `WM_CHAR` 投递，间隔高斯分布（均值 80~150ms），每 10~20 字插入 0.5~2s 停顿；长回复/含链接走剪贴板 + `Ctrl+V`（可靠性优先），发送前校验输入框内容非空。
- **节流与作息**：单会话每分钟回复上限、全局每小时上限、夜间静默时段可配；风控取决于行为模式而非打字节奏，节流优先级高于拟真。
- 发送动作通过 Computer Use 后台输入路径执行，不抢占前台鼠标。

## 回复范围策略

接管面是整个微信号，策略决定例外。配置持久化于 `customer_service/config.json`：

- `scope.mode`：`blacklist`（默认回复全部，名单内屏蔽）| `whitelist`（只回复名单内）。**启用初期默认 whitelist**，验证稳定后再放宽。
- `scope.list`：名单条目（customer_id 为主，备注名为显示）。
- `scope.group_reply`：群聊回复总开关；`scope.group_list`：群级例外名单。
- `scope.quiet_hours`：静默时段（该时段只收不回）。
- `manual_takeover`：人工接管的会话清单（AI 对这些会话静默）。

判定优先级：**人工接管 > 熔断/暂停 > 静默时段 > 黑白名单 > 群聊开关**。被策略排除的消息照常记录日志与计数（`skipped`），不产生任何微信侧动作。

## 身份绑定与上下文管理

**昵称不能作为主键**（对方可改、可重名）；UIA RuntimeId 重启即失效。身份模型：

- 主键：内部 `customer_id`，持久化于 `customer_service/customers.json`。
- 匹配键一级：**备注名**——号主自己设置，不受对方改昵称影响，客服场景本来就有打备注习惯。
- 匹配键二级（锚点）：**微信号 / wxid**——全局唯一。新联系人首次来信时，守护进程自动打开一次资料页读取并绑定到 `customer_id`；此后日常匹配走"备注名 → 微信号"两级查找。
- 冲突处理：备注匹配失败、多义或疑似改名 → 标记为待确认，**宁可漏回，不可回错人**；由巡检会话协助归并，人工确认后落绑定。

**上下文物理隔离**：

```text
customer_service/
  config.json                 # 回复范围策略
  customers.json              # customer_id ↔ 备注 / 微信号 绑定表
  contexts/<customer_id>.md   # 每个客户独立的对话上下文
  status.json                 # 运行状态契约
  logs/                       # 收发审计日志
```

- 一客户一上下文：LLM 输入 = 人设 + 知识库命中片段 + **仅该客户**的历史，跨客户不注入——既防张冠李戴，也防隐私串味。
- 滚动窗口 + 摘要：保留最近 N 条原文，更早历史压缩为摘要附在上下文头部，跨天对话仍记得先前结论，上下文不无限膨胀。
- 群聊单独建模：上下文 key 是群（群级 customer_id），群内消息带发言人归属（"张三说…"），回复可选 @；群上下文为该群共享一份。
- 人设一致性由 `knowledge/persona.md` 保证：所有客户共享同一份人设与话术纪律，历史互不可见。

## 看门狗（第一层监督）

确定性逻辑，不消耗模型：

| 故障 | 检测 | 处置 |
|---|---|---|
| 守护进程崩溃/挂起 | 心跳超时（>2 个轮询周期） | 自动重启 |
| 微信窗口丢失/掉线 | UIA 主窗口查找连续失败 | 尝试重连；需扫码 → 升级人工 |
| UI 布局变化（微信改版） | AX 定位失败率超阈值 | 守护进程自动降级 OCR/视觉；全链路失效 → 升级人工 |
| LLM API 故障 | 调用错误率超阈值 | 消息入队等待重试，不丢消息 |
| 身份解析失败 | 新联系人无法读取资料页 | 该联系人标记待确认，暂不自动回复 |

**熔断**：1 小时内自动重启 >3 次则停止自愈、暂停自动回复、通知人工。任何自动修复不得形成无限循环。

## LLM 巡检（第二层监督）

- 复用 CronService，默认每 30 分钟唤起一次巡检会话（cron 表达式避开整点/半点，如 `17/47 * * * *`，按自动化调度惯例）。
- 巡检输入：`status.json` + 客服日志摘要 + 近期收发样本。
- 巡检职责：回答质量与幻觉判断、知识库缺口记录、异常行为模式（高频重复、答非所问）、待确认身份的归并建议、配置与提示词微调建议/执行。
- 权限边界：巡检会话可修改知识库与客服配置、触发守护进程重启、归并待确认身份；**恢复人工接管、解除熔断**必须显式人工确认。
- 主会话是巡检员与调度员，平时不耗 token，仅巡检时介入。

## 知识库（工作区 markdown）

```text
<workspace>/knowledge/
  index.md        # 索引与检索入口说明
  faq/            # 一问一答：标准问题 + 3~5 个相似问法 + 标准答案
  policy/         # 价格、售后、承诺等敏感事实（唯一事实来源）
  persona.md      # 客服人设与话术风格（亦可由 Skill 策略承载）
```

- 检索纪律由 Skill 策略注入 cowork/客服会话：回答前先检索 `knowledge/`，敏感事实只许引用 `policy/` 原文，禁止编造。
- 隔离性：知识随工作区隔离，多客服工作区互不串味；markdown 可被 git 管理与人工直接编辑。
- 升级路径：知识量增大后在同目录上加 embedding 索引，文档源不变。

## 状态契约

`<workspace>/customer_service/status.json`（守护进程每周期原子写入）：

- `signal`：`on | off | attention` 面板主信号，由守护进程显式写入（离线时由看门狗写入）；`reason`：一句大白话原因（如"静默 23:00–07:00 · 7 条将在 07:00 后发出"），写入方生成，UI 原样呈现。
- `quiet`：静默时段是否生效中（UI 不得按时间自行推断）。
- `heartbeat_at`：最后轮询时间；`wechat_version` / `wechat_window`：窗口状态。
- `counters`：已收/已回/入队/跳过/错误计数；`last_error`：最近错误摘要。
- `circuit_breaker`：重启次数与熔断状态；`mode`：`auto | paused | manual`（人工接管开关）。
- `scope`：生效中的范围模式（`all | whitelist | blacklist`）、两份名单各自条目数、生效中/被排除的会话数。
- `pending_identity`：待确认身份的联系人数量（>0 时巡检与 UI 给出提示）。

UI 呈现只读取该契约映射的显式状态机，不做字符串猜测。

## 呈现层

- 客服面板是 **Content Canvas 一级面板**（surface pill：媒体 / 短剧 / 客服），与 AI 短剧面板、媒体面板同级，不是聊天内嵌卡片；**仅 cowork 会话出现入口**（`session.mode === 'cowork'`，门控判定在服务模块）。视觉随软件 void-light 主题。
- 面板结构（极简定稿，自上而下，扁平分区、发丝线、无瓦片无阴影）：**HERO 大环**（三主态 + 回复率弧 + 进度珠 + reason 一句 + 主操作）→ **今日节奏流线**（24h 收/回平滑曲线 + 静默时段底纹 + 当前时刻墨点）→ **回复范围**（`全部回复`默认 / `指定回复` → 白名单/黑名单两个独立页签，逗号分隔批量输入即时计数，渐进展开）→ **知识库细带**（命中分布一条 + 待清理琥珀提示 + 重新索引/打开目录）→ **规则行**（拟人发送、群聊开关、上限、静默一行收束）。
- **健康信息全隐身**：微信窗口、巡检、计数等正常态不占版面；异常（窗口丢失 / 熔断 / 离线 / 白名单为空）才以 attention 信号出现并写明原因与主操作。
- 名单管理**不做逐用户勾选**：白名单/黑名单为两份独立名单，用户直接输入名字批量维护（逗号/顿号/换行分隔，支持批量粘贴），匹配键为备注名；切回"全部回复"时名单保留并提示。
- 面板**无会话区**：逐会话上下文、指纹去重、接管检测全部归守护进程；面板不罗列会话。
- 面板状态完全来自 `status.json`（`signal` + `reason` + `quiet` + 计数 + 知识库统计）与 `config.json`（scope 两级模型 + 规则）的显式视图模型；UI 不推断运行状态，不硬编码色值（过 `check:theme-colors` 门）。

## 不变量

- 不修改 `remote_connect/bot` 任何行为；两套 IM 能力方向不同、互不干扰。
- 不改变现有 Cron、会话持久化、Skill 策略、Computer Use 工具的既有语义；客服能力全部以新增 service + 配置形式挂载。
- 守护进程重启不得丢失未回复消息（队列与游标持久化先于内存处理）。
- 任何自动修复路径都必须有熔断与人工升级出口。
- 任何消息只注入其所属 customer_id 的上下文；跨客户历史永不混用。
- 身份无法确认时不自动回复；同一条消息永不回复两次。

## 风险

- 个人微信 UI 自动化存在账号风控风险：小号运行、限速、作息模拟、专用运行环境（独立机器/虚拟机），正式商业场景建议评估公众号/企业微信官方 API 通道。
- 微信版本更新可能打碎 UIA 布局：锁定验证过的版本、关闭自动升级、保留 OCR/视觉降级链。
- 锁屏/DPI 变化/窗口最小化影响视觉链路：运行环境约定 + 健康检查前置。
- 资料页 UI 变动影响 wxid 绑定：绑定失败降级为备注名单级匹配并标记待确认，不阻塞既有客户。

## 验证标准

- POC 闭环：在"文件传输助手"上跑通 收消息 → 检索知识库 → 拟人回复 → 日志与心跳落盘。
- 看门狗：杀进程后 2 个轮询周期内自动重启；连续 3 次重启触发熔断并停止自愈。
- 巡检：Cron 按配置间隔唤起巡检会话，能读取 status.json 并产出审查结论。
- 拟人发送：短消息逐字输入且间隔分布符合配置；长消息粘贴路径有输入框非空校验。
- 重启恢复：守护进程重启后不重复回复已处理消息，队列中未回复消息继续处理。
- 策略：whitelist 模式下名单外消息只记录不回复；群聊开关关闭时群消息不入队；静默时段只收不回。
